Docs

StatusDog is an MIT-licensed Node package with zero runtime dependencies. This site is the hosted front end; everything here also runs on your machine.

What this site can and cannot do

Status & availabilityYes — status code, failure reason, what a visitor sees
Response timeYes — total time including redirects
Redirect chainYes — every hop and the final destination
SSL certificateYes — issuer, validity window, days remaining
Body content checkYes — require a string to be present
Uptime historyYes for roster targets, checked on a schedule and stored; your own browser list only accrues while a tab is open
Traffic / visitor countsNo — that needs access to the site's own analytics or server logs, not an external probe

Check API

One request, one probe. Nothing is stored.

GET /api/check?url=example.com
urlrequired · http(s); a bare host gets https:// prepended
expect200, 2xx,3xx, 200-299, * · default 2xx,3xx
containsresponse body must contain this text
methoddefault GET
timeoutmilliseconds, 1000–30000 · default 15000
redirectsfalse to stop following redirects

Private, loopback and link-local addresses are rejected. 

curl "https://status-dog.vercel.app/api/check?url=example.com&expect=200"

24/7 monitoring with the CLI

This browser stops checking when you close the tab. To keep watching a site around the clock, run StatusDog on a machine that stays on. 

git clone https://github.com/alekf9099/StatusDog.git
cd StatusDog && npm install && npm run build
node dist/cli.js init
node dist/cli.js start

start runs the check loop, persists history to data/history.json, and serves a local dashboard on 127.0.0.1:4321.

startRun the check loop and the local dashboard
statusCheck every target once; exits non-zero if any failed
check <url>One-off check, no config file needed
listList configured targets
fallbackServe a maintenance page on its own port
initWrite a starter config file

status and check exit non-zero on failure, so they drop straight into CI or a cron job.

Configuration

statusdog.config.json is discovered from the working directory upwards. // and /* */ comments are allowed. 

{
  "defaults": { "intervalMs": 60000, "failureThreshold": 2 },
  "targets": [
    {
      "id": "api",
      "name": "Public API",
      "url": "https://example.com/health",
      "expectStatus": [200],
      "expectBody": "\"status\":\"ok\"",
      "maxResponseTimeMs": 3000,
      "fallback": { "template": "maintenance", "title": "API unavailable" }
    }
  ],
  "notifiers": [{ "type": "console" }]
}

A target flips to down only after failureThreshold consecutive failures, so one dropped request does not trigger an alert. Full option tables are in the README.

Fallback pages

When a service is down, serve a real maintenance screen instead of a connection error. Three built-in templates, plus your own HTML:

maintenance · error · offline

Standalone, on its own port:

node dist/cli.js fallback --port 8080 --template maintenance

Or inside your own app, gated on a monitored dependency:

import { loadConfig, Monitor, createFallbackMiddleware } from 'statusdog';

const monitor = new Monitor(await loadConfig());
monitor.start();

app.use(createFallbackMiddleware(monitor, {
  targetId: 'payments-api',
  allowPaths: ['/healthz', /^\/webhooks\//],
}));

Requests pass through while the target is up. Once it is confirmed down, everything except allowPaths gets the maintenance page.

Scheduled monitoring, hosted

The dashboard's Monitored 24/7 section is checked by the server and stored, so history accrues with nothing open. Two pieces make that work.

The roster

What gets watched lives in monitors.json, a committed file using the same schema as statusdog.config.json. It is a file rather than a form on purpose: this site has no accounts, so a public write endpoint would let anyone point StatusDog at a URL of their choosing every 15 minutes. Editing the repo is reviewable; a form is not.

The scheduler

POST /api/cron/check probes every roster target and writes the results. It needs a secret, and something has to call it:

CRON_SECRETShared secret. Sent as Authorization: Bearer … or x-cron-secret. Unset means the route is closed, not open.
KV_REST_API_URL
KV_REST_API_TOKEN		A Redis-compatible REST store. UPSTASH_REDIS_REST_* and REDIS_REST_* also work.
STATUSDOG_WEBHOOK_URLOptional. One or more alert webhooks, comma-separated.
STATUSDOG_WEBHOOK_ONOptional. down, up, or down,up (default: both).
STATUSDOG_WEBHOOK_FORMATOptional. full or text; a per-host default applies otherwise.

GitHub Actions does the waking up, every 15 minutes, from .github/workflows/monitor.yml. Vercel's Hobby plan caps cron jobs at once a day, which is useless for uptime monitoring; on a Pro plan you can add a crons entry to vercel.json instead and drop the workflow. GitHub delays scheduled runs under load, so treat 15 minutes as a floor rather than a guarantee.

Until a store is connected, /api/monitors reports storage: "none" and the dashboard says so — the rest of the site keeps working.

Read the results

GET /api/monitors?history=60

Returns each roster target's state, since, last result, uptime and response-time stats, and recent checks. Public and read-only.

Alerts

Set STATUSDOG_WEBHOOK_URL and every confirmed up/down change posts JSON to it. Confirmed is the important word: a transition only happens after failureThreshold consecutive failures, and only the change fires — a target that stays down for a day alerts once, not ninety-six times.

Payload

Two shapes, picked per host. full is the default and carries the whole event, including both text (what Slack renders) and content (what Discord renders), so either works with no adapter: 

{
  "event": "down",
  "previousState": "up",
  "target": { "id": "api", "name": "Public API", "url": "https://example.com/health" },
  "result": { "ok": false, "status": 503, "responseTimeMs": 31, "reason": "status", ... },
  "at": "2026-08-19T07:00:00.000Z",
  "text": "Down: Public API (https://example.com/health) — Unexpected status 503",
  "content": "Down: Public API (https://example.com/health) — Unexpected status 503"
}

text sends only the summary — {"text": "Down: …"} — which strict chat APIs require.

Google Chat

Google Chat validates the body against its Message resource and answers 400 Unknown name "event" on any field it does not recognise, so a rich body fails outright instead of posting a degraded message. chat.googleapis.com therefore defaults to text and needs no extra configuration.

To get the URL: in the space, space name → Apps & integrations → Webhooks → Add webhooks, name it, copy the URL. The ?key=…&token=… query string is the credential and is preserved on delivery.

Delivery

Happens after results are persisted and never fails the run: an unreachable webhook is reported in the response and as a warning on the workflow run, not as a lost check. Only the webhook's origin is ever logged, because the path and query string are the credential.

Running the CLI instead? Put notifiers in statusdog.config.json under notifiers — console and webhook are built in.

Roadmap

Retention is the last 480 checks per target — about five days at a 15-minute interval. Longer history, per-target alert routing, and a public status page per monitor are the obvious next steps.
