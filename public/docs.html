Docs

StatusDog is an MIT-licensed Node package with zero runtime dependencies. This site is the hosted front end; everything here also runs on your machine.

What this site can and cannot do

Status & availabilityYes — status code, failure reason, what a visitor sees
Response timeYes — total time including redirects
Redirect chainYes — every hop and the final destination
SSL certificateYes — issuer, validity window, days remaining
Body content checkYes — require a string to be present
Uptime historyOnly while a dashboard tab is open
Traffic / visitor countsNo — that needs access to the site's own analytics or server logs, not an external probe

Check API

One request, one probe. Nothing is stored.

GET /api/check?url=example.com
urlrequired · http(s); a bare host gets https:// prepended
expect200, 2xx,3xx, 200-299, * · default 2xx,3xx
containsresponse body must contain this text
methoddefault GET
timeoutmilliseconds, 1000–30000 · default 15000
redirectsfalse to stop following redirects

Private, loopback and link-local addresses are rejected. 

curl "https://status-dog.vercel.app/api/check?url=example.com&expect=200"

24/7 monitoring with the CLI

This browser stops checking when you close the tab. To keep watching a site around the clock, run StatusDog on a machine that stays on. 

git clone https://github.com/alekf9099/StatusDog.git
cd StatusDog && npm install && npm run build
node dist/cli.js init
node dist/cli.js start

start runs the check loop, persists history to data/history.json, and serves a local dashboard on 127.0.0.1:4321.

startRun the check loop and the local dashboard
statusCheck every target once; exits non-zero if any failed
check <url>One-off check, no config file needed
listList configured targets
fallbackServe a maintenance page on its own port
initWrite a starter config file

status and check exit non-zero on failure, so they drop straight into CI or a cron job.

Configuration

statusdog.config.json is discovered from the working directory upwards. // and /* */ comments are allowed. 

{
  "defaults": { "intervalMs": 60000, "failureThreshold": 2 },
  "targets": [
    {
      "id": "api",
      "name": "Public API",
      "url": "https://example.com/health",
      "expectStatus": [200],
      "expectBody": "\"status\":\"ok\"",
      "maxResponseTimeMs": 3000,
      "fallback": { "template": "maintenance", "title": "API unavailable" }
    }
  ],
  "notifiers": [{ "type": "console" }]
}

A target flips to down only after failureThreshold consecutive failures, so one dropped request does not trigger an alert. Full option tables are in the README.

Fallback pages

When a service is down, serve a real maintenance screen instead of a connection error. Three built-in templates, plus your own HTML:

maintenance · error · offline

Standalone, on its own port:

node dist/cli.js fallback --port 8080 --template maintenance

Or inside your own app, gated on a monitored dependency:

import { loadConfig, Monitor, createFallbackMiddleware } from 'statusdog';

const monitor = new Monitor(await loadConfig());
monitor.start();

app.use(createFallbackMiddleware(monitor, {
  targetId: 'payments-api',
  allowPaths: ['/healthz', /^\/webhooks\//],
}));

Requests pass through while the target is up. Once it is confirmed down, everything except allowPaths gets the maintenance page.

Roadmap

Persistent server-side monitoring — uptime history that keeps accruing with no browser open — needs a database and a scheduler. That is the next step; the engine, the API and this front end are already in place for it.
